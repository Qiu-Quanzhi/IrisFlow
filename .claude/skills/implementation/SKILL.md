# 待发布内容实现

## 触发条件

用户说 "实现待发布"、"执行待发布"、"implement changelog"、"按 CHANGELOG 开发" 或类似表述。

## 流程

### 1. 读取待发布内容

从 `CHANGELOG.md` 顶部提取 `# 待发布` 章节的文本。

该文本位于文件头部 `# Changelog` 标题与下一个 `## X.Y.Z` 版本条目之间。提取时：
- 忽略 `# Changelog` 标题行
- 忽略元数据行（格式说明、语义化版本链接）
- 提取 `# 待发布` 标题之后、下一个 `##` 版本标题之前的所有内容

### 2. 解析为开发任务

将待发布文本解析为可执行的开发任务列表：

- **破坏性更新** / **BREAKING CHANGE** — 涉及不兼容 API 修改，需先全面理解现有架构再动手
- **功能描述** — 按自然语言描述拆分为独立任务，每个任务应有明确的验收标准
- **允许自由调用工具与引入依赖** — 意味着可以根据需要安装/添加任何第三方库、运行任意命令来完成任务

如果待发布内容描述的变更范围较大或涉及架构调整，**进入 Plan Mode** 先设计方案再编码。

### 3. 实现

逐任务实现，遵循以下原则：

- **先理解再动手** — 阅读受影响的现有代码，理解当前架构与设计模式
- **匹配现有风格** — 新代码在命名、注释密度、错误处理方式上与周围代码一致
- **允许引入新依赖** — 当任务明确允许时，使用 `uv add`（Python）/ `pnpm add`（Node.js）添加库
- **保持向下兼容** — 除非待发布明确标注"破坏性更新"

对于标注了 **破坏性更新** 的条目：
- 先梳理所有受影响的调用方
- 统一修改，确保没有遗漏
- 在提交信息中标注 `BREAKING CHANGE`

### 4. 验证

实现完成后：
- 检查所有受影响的文件是否有语法错误（lint/diagnostic）
- 如有测试，运行测试
- 确认新代码可被导入且无运行时错误

### 5. 汇报

列出所有修改/新增的文件及变更摘要，供用户确认。待用户确认后，**不要**自动执行版本更新 —— 用户可随后单独调用 `/version-bump`。

### 6. Git 提交

提交信息遵循 Conventional Commits 格式：
- `feat: 简短描述` — 功能性变更
- `fix: 简短描述` — 问题修复

对于破坏性变更，在提交正文中标注 `BREAKING CHANGE: 描述`。

**重要**：提交信息中**禁止**添加 `Co-Authored-By:` 行。

## 示例

```
用户: "实现待发布"

→ 1. 读取 CHANGELOG.md → 待发布: "将含有外部网络请求的接口异步化"
→ 2. 解析为任务: [扫描所有同步 HTTP 调用, 改为 async/await, 更新调用方]
→ 3. 进入 Plan Mode 设计方案
→ 4. 逐文件实现
→ 5. 验证并汇报
```
